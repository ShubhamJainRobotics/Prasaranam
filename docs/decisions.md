  - **Choice**: Target Node.js `^24.21.0` (or `24.x`) and npm `^12.1.0`.
  - **Reason**: Observed active environment runs Node `v24.21.0` and npm `12.1.0`. Section 2A.16 requires recording the supported LTS Node release and pinning dependencies.

  - **Choice**: Explicitly ignore `.env` and all `.env.*` patterns while whitelisting `!.env.example` and `!.env.*.example`.
  - **Reason**: Security Invariants 7 & 10 require secrets to never be committed or reach repositories, while Section 1.1 Item 8 and Section 2A require `.env.example` templates for configuration.
- **Date**: 2026-11-07
  - **Question**: Which Zod major version should be installed in Phase 1 (`zod@3` vs `zod@4`)?
  - **Choice**: Pin `zod@^3.24.2`.
  - **Reason**: Verified empirically that `zod-to-json-schema` (required by Section 2A.16 for generating committed JSON Schemas) fails to extract properties when running against `zod@4.6.7` due to internal `_def` schema restructuring, whereas `zod@3.24.2` produces full, valid schemas.
- **Date**: 2026-11-07
  - **Question**: How should package inter-dependencies be resolved across workspaces?
  - **Choice**: Use TypeScript project references and package exports (`"exports": { ".": { "types": "./src/index.ts", "default": "./src/index.ts" } }`) for fast development and build interoperability across tsx, vite, vitest, and tsc.
  - **Reason**: Satisfies Section 20 without requiring circular intermediate build passes.
- **Date**: 2026-11-07
  - **Question**: How should `pgcrypto` functions be referenced inside `SECURITY DEFINER` functions with `search_path = ''`?
  - **Choice**: Fully schema-qualify all pgcrypto calls as `extensions.digest(...)`.
  - **Reason**: In Supabase PostgreSQL, extensions are installed in the `extensions` schema. With `search_path = ''`, unqualified function calls fail with `function does not exist`.
- **Date**: 2026-11-07
  - **Question**: What should the initial `access_epoch` of a freshly created project be after inserting the initial owner?
  - **Choice**: Project creation starts at `access_epoch = 1`. In `create_project`, resetting `access_epoch = 1` after inserting the initial owner ensures a fresh project begins at epoch 1 per Section 10 default, with subsequent membership and grant changes incrementing the epoch.
  - **Reason**: Section 10 defines `access_epoch bigint not null default 1`. The membership-change trigger on `project_members` fires when inserting the owner; resetting to 1 ensures clean initial state.
- **Date**: 2026-11-07
  - **Question**: How are string offsets calculated across JavaScript and PostgreSQL for multi-byte Unicode characters and emoji?
  - **Choice**: Use Unicode code points (characters). PostgreSQL `char_length()` and `substring(... from ... for ...)` operate on code points in a UTF-8 database. In JavaScript, code-point-aware iteration (`[...str].length`) must be used instead of UTF-16 code units (`str.length`).
  - **Reason**: SPEC Section 2A.6 item 3 explicitly requires zero-based indices in Unicode code points, not UTF-16 code units or bytes.

## Spec issues

- **Section 2A.2 line 79 vs Replace-by-Revision**: The specification notes that contributors can import sources, but also states that replace-by-revision archives the prior source version. Since archiving sources requires the `owner` role, replace-by-revision was restricted to project owners to prevent privilege escalation (archiving sources without owner permission).
- **Leased Job Return Columns**: SPEC Section 2A.11 mentions `lease_job` returns job fields for execution. Because `public.ai_usage` requires `user_id` to log AI token consumption and latency per Section 10, `requested_by` was explicitly returned from `app_private.lease_job` to satisfy the database foreign key invariant without additional queries.
- **Handover Approval Precondition and Attestation Mapping**: SPEC Section 2A.4 item 7 requires `confirmReviewedForRecipient = true` and 0 pending items. In `app_private.approve_handover`, pending items raise `PRECONDITION_FAILED` (HTTP 409), whereas missing reviewer attestation confirmation raises `VALIDATION_ERROR` (HTTP 422), providing clear and distinct status signals to the UI.
- **Audit Action for Handover Approval**: `public.reviews` column uses `review_action` enum type (`approve_version`, `approve_claim`, `reject_claim`, etc.). Handover approvals insert `approve_version` into `public.reviews` and `handover.approve` into `public.audit_events`, ensuring both granular review logs and compliance audit trails.
- **`ai_usage.purpose` Naming for Q&A**: SPEC Section 15.5 references Q&A generating an answer. The database schema in Section 10 defines `ai_usage_purpose_check` with `'answer'` rather than `'qa'`. Implemented with `'answer'` to maintain database schema integrity.
- **Recipient Access to Approved vs Shared Handovers**: SPEC Section 2A.9 item 2 specifies that handovers are visible to recipients only when status is `shared`. When a handover is merely `approved` (and not yet shared), export and view attempts by recipients return HTTP 409 `REGENERATION_REQUIRED` / inaccessible until the reviewer explicitly shares it.
- **Section 22.3 Negative Test Suite Limitation**: In accordance with Section 22.3, a finite automated negative test suite does not guarantee zero leakage in all hypothetical edge cases. Threat modeling, defense-in-depth isolation, and rigorous continuous monitoring are detailed in `docs/threat-model.md` and `docs/operations.md`.
- **Recipient Isolation on Project Handover Detail**: SPEC Section 2A.4 and Section 2A.9 item 2 state that shared handovers are readable only by the named recipient, but did not explicitly specify the exact HTTP status code for a recipient attempting to view another recipient's draft or approved handover within the same project. To uphold Section 11.2 and Section 18.1 (preventing existence probing and resource enumeration), the API returns HTTP 404 `NOT_FOUND` with a standard empty error envelope, matching the response returned for completely nonexistent resources.
- **Date**: 2026-11-08
  - **Question**: How should scenario-runner isolate burst rate limiting tests without contaminating global test suite IP quotas?
  - **Choice**: The global rate limiter is configured with `RATE_LIMIT_MAX_REQUESTS: 2000` to prevent interference across the multi-scenario suite. In Scenario 9 (`scn9-step-02-rate-limiting`), an isolated test application instance is constructed via `createApp({ env: { ...ctx.env, RATE_LIMIT_MAX_REQUESTS: 5 }, pool: ctx.pool })` to test burst 429 response codes and `Retry-After` headers independently without exhausting the client IP budget for subsequent scenarios.
  - **Reason**: Running burst rate limit checks on the shared application instance exhausted the IP allowance, causing cascading 429 failures in subsequent scenarios. Ephemeral application instantiation isolates rate limiting verification.
- **Date**: 2026-11-08
  - **Question**: How should foreign key cascading deletes be handled during synthetic scenario resets?
  - **Choice**: In `resetScenarioData()`, demote any approved or shared handovers to `status = 'draft'` first (preventing `enforce_handover_immutability()` triggers from blocking deletion), and explicitly delete `public.reviews`, `public.handover_item_claims`, `public.handover_items`, and `public.handovers` for all `scn-%` projects before deleting projects.
  - **Reason**: The foreign key `handover_item_claims_claim_id_project_id_fkey` on `public.handover_item_claims` references `public.claims(id, project_id)` without an `ON DELETE CASCADE` clause. Explicit deletion in child-to-parent order avoids foreign key violation 23503 during cleanup.
- **Date**: 2026-11-08
  - **Question**: How should asynchronous AI background jobs (extraction, handover generation) be executed during Playwright UI flows?
  - **Choice**: Instantiate and start an in-process `RelayWorker` instance wired to the test database pool and fake deterministic provider during `test.beforeAll`, stopping it in `test.afterAll`.
  - **Reason**: Playwright `webServer` configuration launches only the API and Web Vite dev servers. Without an active worker process polling the `jobs` table, background extraction and handover generation jobs remain queued, leaving handover review pages without generated drafts.
- **Demoting Last Project Owner (SPEC Section 11.1 / Section 12)**: SPEC specifies last-owner protection to prevent organisations and projects from becoming ownerless. In `PATCH /api/v1/projects/:id/members/:userId`, attempting to demote or deactivate the last active owner currently returns HTTP 200 rather than HTTP 409 `LAST_OWNER`, leaving the project without an active owner. Recorded as an application defect.
- **Demoting Last Organisation Owner Status Code (SPEC Section 11.1 / Section 12)**: Attempting to demote or deactivate the last active organisation owner returns HTTP 403 `FORBIDDEN` rather than the required HTTP 409 `LAST_OWNER`. Recorded as an application defect.
- **Project Member Invitation Non-Enumeration (SPEC Section 18.1)**: Inviting an unknown email address to a project via `POST /api/v1/projects/:id/members` returns HTTP 404 `NOT_FOUND` rather than a non-enumerating generic success response (HTTP 200/201), allowing attackers to enumerate registered users across the platform. Recorded as an application defect.
- **Tenant Isolation: Organisation Admin Project Access (SPEC Section 2A.2)**: SPEC Section 2A.2 explicitly states: "Organisation admins have no automatic access to project data: they cannot see titles, counts, sources, claims, handovers, questions, or conversation messages for projects they do not belong to." However, `GET /api/v1/projects/:id` allows organisation admins without project membership to view the project summary (HTTP 200). Recorded as an application defect.
