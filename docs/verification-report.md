## 1. Executive Summary & Audit Methodology

This report documents the independent verification of the Relay codebase against `docs/SPEC.md`, `docs/decisions.md`, and all security invariants. The audit was conducted from an adversarial perspective:

- All `node_modules` and build outputs were removed prior to running tests from a completely clean state.
- The PostgreSQL database was cleanly re-initialized with all 24 database migrations applied from scratch via `npm run db:reset`.
- Full static analysis was executed: `npm run typecheck`, `npm run lint`, and `npm run format:check`.
- The complete test pyramid was executed: unit tests, integration tests, security tests, an adversarial attack pass, and end-to-end browser tests via Playwright.
- Source code was searched for placeholders, forbidden imports, client leaks, and authorization oversights.
- Production web bundle artifacts and Docker container images were inspected for secret leakage.

### Defect Discovered and Resolved

During the Attack Pass (Attack 1: Recipient B reading Recipient A's handover), an authorization gap was identified in `apps/api/src/auth/authorisation.ts` and `apps/api/src/routes/handovers.ts`:

- **Vulnerability:** When handling `HANDOVER_VIEW` for `GET /api/v1/handovers/:id`, the route handler and authorization middleware checked whether the caller was a project member, but if the caller had the `recipient` role in the project and was _not_ the designated recipient of that specific handover (`h.recipient_id !== caller.id`), the handler did not reject the request, allowing Recipient B to view Recipient A's handover items.
- **Remediation:**
  1. Updated `apps/api/src/auth/authorisation.ts` under `HANDOVER_VIEW` and `HANDOVER_EXPORT` to verify that when caller has the `recipient` role, `h.recipient_id === caller.id` is strictly enforced, returning `404 NOT_FOUND` otherwise (preventing resource existence probing per Section 11.2 & 18.1).
  2. Added defense-in-depth checks to `GET /handovers/:id`, `GET /handovers/:id/export`, and `GET /handovers/:id/reviews` in `apps/api/src/routes/handovers.ts` rejecting callers who are neither reviewers/owners nor the designated recipient with HTTP 404 `NOT_FOUND`.
- **Regression Verification:** Added dedicated test in `tests/security/attack-pass.test.ts` verifying that Recipient B requesting Recipient A's handover receives HTTP 404 `NOT_FOUND` with zero title, section, or item leaks.

## 7. Known Limitations

1. **Finite Automated Test Suite:**
   In accordance with Section 22.3 and Section 2A.4 Item 6, automated test suites do not mathematically guarantee zero data leakage. Human review and explicit reviewer attestation (`confirmReviewedForRecipient`) remain a mandatory defense-in-depth safeguard against human reviewers inadvertently copying confidential details into free-text item wording.
2. **Deterministic Fake AI Provider:**
   In test and demo environments, simulated structured output is generated using the deterministic rule-based provider (`FakeDeterministicProvider`). Production verification requires a live Google Gemini API key configured with `GEMINI_API_KEY`.
3. **In-Memory Rate Limiting:**
   API rate limiting uses `express-rate-limit` with an in-memory store suitable for single-instance container deployments. Multi-instance cluster scaling would require backing the rate limiter with Redis.
